# test-engine/CLAUDE.md — 심리테스트 콘텐츠 자동 생성 시스템

이 문서는 `/test-engine/` 폴더 전용 작업 규칙이다. 메인 사이트의 `/CLAUDE.md`(아키텍처 규칙)와는
별개이며, 새 심리테스트 콘텐츠를 추가할 때마다 항상 이 순서를 따른다.

## 트리거
사용자가 다음처럼 요청하면 아래 4-1~4-7 절차를 자동으로 따라 진행한다.
> "새 심리테스트 추가해줘: {주제, 문항, 있다면 결과구간}"

또는 md 파일로 여러 개(예: 20개)를 한 번에 전달한 뒤:
> "다음 3개(또는 원하는 개수) 제작해줘" / "이어서 만들어줘"

## 관련 파일
```
/test-engine/
  CLAUDE.md              # 이 파일 — 작업 규칙 전체
  progress.md             # 진행상황 대시보드(체크리스트+세션 로그) — 세션 시작 전 항상 먼저 읽을 것
  tests/
    index.json           # 콘텐츠 레지스트리 — 새 테스트 작업 전 항상 먼저 읽을 것
  style-guide.md          # 콘텐츠 톤 스타일 누적 기록 — 새 테스트 작업 전 항상 먼저 읽을 것
```

---

## 4-1. 입력 형식
사용자가 "새 심리테스트 추가해줘" + 주제/문항(+선택적으로 결과구간)을 준다.
- 문항만 주어지고 결과 구간이 없으면, 기존 완성 테스트 톤을 참고해 초안을 작성하고
  **먼저 보여주고 승인받는다.**
- **질문/선택지 문장은 항상 상황을 풀어서 쓴 완결된 문장으로 작성한다(2026-07-10 확정)** —
  "본인 유형은?", "처음 만난 사람에게?"처럼 뚝뚝 끊긴 단답형 질문은 금지. "OO할 때, OO에서
  나는 어떻게 할까?"/"OO라면, 나의 반응은?"처럼 상황을 먼저 설명하고 그 안에서 어떤 선택을
  하는지 묻는 형태로 쓴다. 선택지도 "먼저 말 검"처럼 어미가 잘린 메모체가 아니라 자연스러운
  구어체 문장으로 끝맺는다(예: "낯선 사람한테도 먼저 말 걸며 분위기를 트는 편" 등). 기존
  테스트를 리라이팅할 때도 `choice.type`/`axis`/`score`/`tag` 등 채점에 쓰이는 필드값은
  절대 건드리지 않고 `text`/`label` 텍스트만 교체한다.

## 4-2. 사전 체크
- `tests/index.json` 읽고 id 중복, concept_style 반복 여부 확인.
- scoring_type 판단: 일반 테스트는 sum 또는 type, **MBTI 16유형(4축 동시 산출)은 `mbti4`**
  (겉/속처럼 두 세트를 동시에 산출해야 하면 `mbti4_dual`, 사용자 자기신고 값과 비교하고
  싶으면 인트로에 `intro_input` 드롭다운 추가 — 전부 STEP 5에서 추가된 기능, 아래 참고).
  기존 `axis`는 좌/우 단일 축 게이지 1개만 지원해서 16유형 MBTI 산출엔 못 쓴다.
  (엔진은 sum/type/quiz/axis/mbti4/mbti4_dual 6종을 지원하므로 이 범위 안에서는 엔진 코드를
  재작업하지 않는다. 이 6종으로 표현 안 되는 완전히 새로운 상호작용(예: #19 커플 궁합기처럼
  "두 유형을 골라 즉시 매칭"하는 화면)은 여전히 엔진 확장이 필요해 사전 보고 후 진행한다.)
- **STEP 4(2026-07-10)부터 예외 1건**: `sum` 채점에 선택적 보조 태그 집계 기능이 추가됨 —
  문항 선택지에 `"tag"` 필드를 넣으면(등급 판정용 `score`와 별개로) 가장 많이 나온 태그가
  `result.tag`로 결과에 merge되고, 결과 텍스트(`subtitle`/`traits[]`/`tip`)에 `{tag}` 플레이스홀더를
  쓰면 렌더 시점에 자동 치환된다(태그가 하나도 안 걸렸으면 결과 항목의 `tagFallback` 값으로 대체,
  `villain-index/config.json` 참고). "등급(sum)"과 "페르소나 유형(태그)"을 동시에 매기는 콘텐츠에만
  쓰는 기능이라 필요할 때만 선택지에 `tag`를 붙이면 되고, `tag`가 없는 기존/향후 `sum` 테스트(예:
  mental-age)는 완전히 그대로 동작한다(하위호환 확인됨). 이 예외를 제외한 나머지 엔진 로직은
  여전히 "절대 수정하지 않는다"는 원칙을 유지 — `sum` 채점 자체의 새 기능이 또 필요해지면
  이번처럼 사용자에게 먼저 영향 범위·리스크를 보고하고 컨펌받은 뒤에만 진행할 것.
- **STEP 5(2026-07-10) 예외 2건째**: MBTI 시리즈 10개를 만들다 기존 `axis`(좌/우 단일 축)로는
  16유형 MBTI(4축 동시 계산)가 애초에 불가능하다는 걸 발견 — 사용자가 "복잡하더라도 퀄리티를
  높이는 쪽"으로 확정해 신규 `mbti4`/`mbti4_dual` scoring_type과 인트로 `intro_input` 드롭다운을
  추가(engine.js 상단 STEP 5 코멘트, `test-engine/README.md` 참고). `choice.axis`/`question.block`/
  `config.intro_input`이 전부 없는 기존 config는 렌더링·채점에 변화가 없다(mental-age/villain-index
  둘 다 Playwright로 재검증). `real-vs-fake-mbti`(mbti4_dual)와 `ai-mbti-judge`(intro_input)가
  실사용 예시. **#19(MBTI 커플 궁합기)는 이 6종 중 어느 것으로도 표현이 안 되는 "두 유형을 골라
  즉시 매칭"하는 화면이라 이번 STEP에 포함하지 않음** — 콘텐츠·등급 규칙만 `tests/mbti-couple-match/
  DESIGN.md`에 정리해두고, 실제 구현(신규 화면 타입)은 사용자 확인 후 별도 진행.
- **STEP 6(2026-07-10) 예외 3건째 — #19 대체**: 사용자가 "궁합 말고 다른 걸로, 근데 MBTI식은
  유지"로 결정해 #19를 `mbti-stat-window`(MBTI를 게임 캐릭터 능력치 스탯 바로 시각화)로 교체
  확정. `mbti4`는 이미 축별 비율을 내부적으로 계산해두고 있었는데 `fillVarsTemplate`에는
  `{code}`/`{claimed}`만 노출되고 있어서, 이미 계산된 값을 `{e}`/`{n}`/`{f}`/`{j}`(E/N/F/J
  쪽 퍼센트)와 `{ebar}`/`{nbar}`/`{fbar}`/`{jbar}`(10칸 이모지 막대 문자열)로 템플릿에 추가
  노출(engine.js `computeMbti4Result`/신규 `statBar()`, 새 scoring_type이 아니라 mbti4의
  파생값만 더 꺼내 쓰는 것). 이 변수들을 참조하지 않는 기존 resultTemplate은 완전히 그대로
  동작(mental-age Playwright 재검증 완료), `mbti-stat-window`가 실사용 예시 — 16유형 고정
  문구가 아니라 **실제 응답 기반 퍼센트**가 나오는 첫 mbti4 콘텐츠.

## 4-3. 폴더 생성
```
/test-engine/tests/{number}-{test_id}/
  index.html   (기존 완성 테스트의 index.html 복사 후 data-test-id만 교체)
  config.json
  assets/
```
**폴더명은 `tests/index.json`의 `number` 필드를 앞에 붙인다**(예: `1-k-office-type`,
`11-real-vs-fake-mbti`, 2026-07-10 사용자 요청 — 파일 탐색기에서 순서 파악이 쉽도록).
`number`가 없는 mental-age(20개 목록 이전 1호 콘텐츠)만 예외. **주의**: 폴더명이 곧
공개 URL 경로(`/test-engine/tests/{폴더명}/index.html`)이므로, 폴더를 만든 뒤에
번호가 바뀌는 일이 없도록 착수 전 `index.json`에서 번호를 먼저 확정할 것 — `config.json`
내부의 `"id"` 필드나 `index.html`의 `data-test-id`는 번호 없는 순수 test_id 그대로 유지
(localStorage 완료 카운터 키 등에 쓰이므로 폴더명과 다르게 둬도 무방, 실제로도 다름).
기존 엔진 파일(engine.js/engine.css/themes/*)은 절대 수정하지 않는다.
**`index.html`을 복사할 때 `engine.css`/`engine.js` 스크립트 태그 다음 줄에 있는
`engage.css?v=1`/`engage.js?v=1` 태그 2줄도 그대로 딸려오는지 확인할 것** — 댓글 기능은
2026-07-14부터 모든 신규 콘텐츠의 표준 구성요소다(4-5 참고).

## 4-4. 이미지 — 샘플 우선 승인 절차 (★ 핵심, 항상 준수)
1. `style-guide.md`를 참고해 이 테스트에 **가장 재미있게 어울리는 톤**(병맛/진지·감성/
   깔끔·위트/밈·드립 중 선택, 섞어도 됨)을 정하고, 그 톤에 맞는 "컨셉 한 줄"을 작성.
   주제 성격과 안 맞는데 병맛만 억지로 넣지 않는다. 최근 3회 이상 반복된 톤·컨셉은
   피하고 새로운 조합을 제안한다. **이미지 매체(렌더링 기법)도 마찬가지 원칙** —
   `style-guide.md`의 "이미지 매체 다양성 원칙" 절의 "사용된 매체 목록"을 먼저 확인해
   겹치지 않는 매체를 고른다(팔레트만 바꾸는 건 다른 매체로 치지 않음, 2026-07-10
   피드백). UI 테마(`themes/*.css`)도 이 매체에 맞춰 함께 새로 설계한다.
2. 커버 1컷 + 결과 이미지 중 1~2컷만 먼저 상세 프롬프트를 만들어 **보여주고 승인받는다.**
   (전체 이미지를 한 번에 생성하지 않는다.)
3. **2단계 워크플로우(2026-07-10~, 기본값·사실상 무료)**: OpenAI(`gpt-image-1`) 텍스트 단독 생성
   품질이 부족할 때 아래 방식으로 전환함 — 이 문서의 "샘플 우선 승인" 원칙 자체는 동일하게 유지.
   - **1단계(스타일 탐색, 무료·수동)**: 승인된 컨셉의 포터블 프롬프트를 사용자에게 그대로 전달 →
     사용자가 Gemini 무료 채팅(gemini.google.com, API 아닌 소비자 앱이라 결제 불필요) 등 외부 툴로
     레퍼런스 이미지 1장을 직접 뽑아 전달한다.
   - **2단계(프로덕션 자동화, 건당 수 센트)**: 받은 레퍼런스 이미지를
     `tests/{testId}/assets/reference/`에 넣고 기존 `generate-assets.js`를 그대로 실행 —
     `reference/`가 있으면 자동으로 OpenAI `images/edits`(레퍼런스 최대 16장, 스타일 전이 지원)로
     전환돼 나머지 세트를 그 스타일로 생성한다(신규 결제 설정 불필요, 이미 등록된
     `OPENAI_API_KEY` 재사용, 2026-07-10 실제 호출 200 OK 검증 완료). `reference/`가 없으면
     기존처럼 순수 텍스트 생성 그대로 동작(하위호환).
   - **대안(참고용, 결제 필요)**: 사람 개입 없이 완전 자동화하고 싶으면 `generate-assets-gemini.js`
     (Nano Banana Pro)도 있으나 Gemini API는 무료 티어가 없어 결제 활성화가 필요함 — 지금은 위
     방식으로 충분해 우선순위 낮음. 상세는 `test-engine/README.md`의
     "이미지 생성 2단계 워크플로우" 절 참고.
4. "오케이" 받으면 나머지 전체(결과 구간 등)를 같은 톤/레퍼런스로 일괄 생성한다.
5. 수정 요청이 오면 톤/컨셉/프롬프트를 고쳐 다시 1~2장만 시도한다 (전체 재생성 금지).
6. 이미지 생성은 빌드타임 스크립트로 처리하고(런타임 API 호출 금지), API 키는
   Codespaces Secrets로 관리한다(`OPENAI_API_KEY`/`GEMINI_API_KEY`).

## 4-4-1. 문항(질문) 이미지 규칙 (2026-07-10 제정 → 같은 날 재확정)
`questions[].image`는 nullable — **선택지가 3개 이상인 문항형 테스트는 문항 이미지를 넣지
않는다**(선택지 버튼 자체가 화면을 채워서 비어 보이지 않음, `type`/`sum` 채점 다수가 여기
해당). **선택지가 1~2개뿐인 문항형 테스트(주로 MBTI 4축 계열 `mbti4`/`mbti4_dual`, A/B
이지선다라 화면 가운데가 많이 빔)는 전체 문항 중 절반 정도(예: 8문항이면 1/3/5번, 15문항이면
1/4/7/10/13번처럼 3칸 안팎 간격)에만 문항 이미지를 넣어 허전해 보이지 않게 한다** — 매
문항마다 넣을 필요는 없음.

**문항 이미지는 항상 Claude가 직접 SVG로 제작한다(API 생성 금지, 비용 발생 지점 아님) —
2026-07-10 한 차례 "API(images/edits)로 전환"을 시도했다가 비용 부담(10~20장 단위로도 몰입테스트
20개 전체 환산 시 수 달러) 때문에 같은 날 SVG로 재확정, 앞으로도 이 방침 유지.** 커버/결과
이미지(4-4)만 API로 만들고 문항 이미지는 항상 무료 SVG로 만드는 이유는 문항 이미지는 "빈 공간을
심심하지 않게 채우는 보조 요소"이지 결과 화면처럼 소장·공유 욕구를 자극해야 하는 핵심 자산이
아니기 때문 — 개수도 훨씬 많아(문항마다 필요) 전부 API로 돌리면 비용이 빠르게 불어난다.

**단, SVG라고 대충 만들면 안 된다(2026-07-10 사용자 피드백)** — "중간에 삽입된 이미지가 너무
관련 없어 보이는 이미지"라는 지적을 받은 적 있음. 반드시 **그 문항의 질문·선택지 내용을 먼저
읽고, 그 상황을 구체적으로 형상화하는 그림**을 그릴 것(예: "친구들 사이에 갈등이 터졌다" 문항엔
싸우는 두 사람+중재하는 나를 그리는 식, "취기가 오르면 감정이 어느 쪽으로 터질까" 문항엔 팩폭
번개 아이콘과 눈물방울 아이콘처럼 선택지 자체를 시각화하는 식). 아무 문항에나 재사용 가능한
장식용 도형(하트/말풍선/느낌표 낙서 등)만 반복해서 붙여넣지 말 것 — 그 문항에서만 나올 수 있는
장면인지 스스로 점검한다. 그 테스트의 테마 색상(브랜드 청록/주황 + 테마별 팔레트)에 맞춰 제작.

## 4-5. 배포 연동
- **댓글 기능은 모든 신규 콘텐츠의 표준 구성요소다(2026-07-14 확정)**: `index.html`에
  `<link rel="stylesheet" href="../../engage.css?v=1">`(engine.css 태그 다음 줄)와
  `<script src="../../engage.js?v=1" defer></script>`(engine.js 태그 다음 줄)를 항상 포함한다.
  `engage.js`는 `MutationObserver`로 인트로 화면의 `.te-choices-fixed`(시작 버튼) 등장을
  감지해 `.te-app`의 마지막 자식으로 댓글 패널을 자동 마운트하므로, 이 두 줄만 넣으면 `id`
  필드(=`data-test-id`)를 자동으로 읽어 `section:'testengine', item_id:{id}`로 댓글이
  연결된다 — 이 파일 안에서 추가로 손댈 코드는 없다. **반응 버튼(저장/소름돋/빵터짐/킹정)은
  설계만 해두고 구현 보류 중**(저장 버튼이 로그인+마이페이지 스크랩 연동을 전제로 하는 기능이라,
  로그인 기능이 test-engine까지 확장되기 전엔 의미가 약하다고 판단 — 재개 시

- 메인 사이트 `data.js`의 `AppData.externalTests`(몰입테스트) 또는 `AppData.mbtiZoneTests`

## 4-7. 여러 개를 몰아서 만들 때 (예: 20개 목록을 md로 한번에 전달한 경우)
- 사용자가 "다음 n개 제작해줘"라고 요청하면, 이전에 완료된 항목을 `tests/index.json`에서
  확인하여 **그 다음 순번부터 n개**를 진행한다 (전체를 한 번에 만들지 않는다).
- 이미지 샘플 승인 절차(4-4)는 배치 내 테스트마다 각각 지킨다 (n개를 뭉쳐서 한 번에
  승인받지 않는다).
- 각 배치 작업을 시작하기 전, 전체 목록 대비 **"현재 몇 개 중 몇 개 완료됐는지"**를
  먼저 요약해서 보여준다. 예) "전체 20개 중 5개 완료. 6~8번(총 3개) 진행할게요."
- 배치가 끝나면 같은 형식으로 갱신된 진행 현황을 다시 보고한다.
  예) "8/20 완료. 다음은 9번부터입니다."
- 사용자가 몇 개를 만들지 정확히 지정하지 않고 "이어서 만들어줘"라고만 해도,
  마지막으로 완료된 지점부터 이어가며 진행 현황을 매번 보고한다.
- **QA "통과"는 항상 전수 검증을 의미한다 — 일부만 샘플로 확인하고 "통과"라고 보고하지
  않는다(2026-07-12 사용자 지적).** 엔진(engine.js/engine.css) 레벨 수정처럼 "20개 전부에
  동일하게 적용되는 구조라 로직상 전부 통과할 것"이라는 추론만으로 일부(예: 5~7개)만 확인하고
  전체가 통과했다고 말하지 말 것 — 실제로 스크립트를 돌려 21개(또는 해당 배치 전체) 각각을
  전부 재생·검증한 뒤에만 "N/N 통과"라고 보고한다. 로컬 서버로 검증했다면 push 이후 실제
  라이브 사이트에서도 같은 전수 검증을 한 번 더 하는 것을 기본으로 한다(이 프로젝트는
  브랜치가 하나뿐이라 push=즉시 자동배포이므로, 로컬 검증과 라이브 검증이 별개 단계로 필요함).

## 4-8. 진행상황 기록 (progress.md) — 세션 끊김 대비 (2026-07-11 제정)
사용자가 토큰 소진이나 코드스페이스 세션 종료로 작업 중간에 끊기는 경우를 겪은 뒤 확정한 규칙.
**핵심은 "완료 단위 = 커밋 단위"로 맞추고, `progress.md`는 그 커밋들을 한눈에 보는
대시보드로 쓰는 것.**

- **세션을 시작할 때 항상 `test-engine/progress.md`를 먼저 읽는다** — `[~]`(진행 중)나
  `[ ]`(대기) 상태가 있으면 그 지점부터 이어서 진행하고, 이미 끝난 걸 처음부터 다시 만들지 않는다.
- **커밋 타이밍**: 테스트 1개가 완전히 끝날 때만(문항+답변+이미지+채점 스키마 전부) 커밋한다.
  문항만 쓴 상태, 이미지 생성 전 상태 같은 중간 산출물에서는 커밋하지 않는다 — "완료" 단위로만
  커밋해야 나중에 `git log`만 봐도 뭐가 진짜 끝난 건지 헷갈리지 않는다.
  커밋 메시지 예: `feat: 심리테스트 #7 몰입테스트 제작완료`
- **커밋 직후 `progress.md`를 갱신**한다 — 해당 항목을 `[x]`로 바꾸고 commit hash를 적어넣는다.
  **아직 완료되지 않은 항목은 절대 `[x]`로 표시하지 않는다** — 진행 중이면 `[~]`와 함께 정확히
  어느 단계까지 됐는지(예: "문항 작성 완료, 이미지 생성 전") 적어서, 다음 세션이 그 설명만 보고
  바로 이어받을 수 있게 한다.
- `progress.md`의 "세션 로그" 절에 타임스탬프+무엇을 했는지/어디서 끊겼는지 짧게 남긴다.
- **"완료([x])"의 정의는 콘텐츠 제작(문항/답변/이미지/채점)까지이며, 사이트 연동(4-5)은
  포함하지 않는다** — 연동 여부는 progress.md에 별도 컬럼/표기로 관리한다.
- **예약(스케줄)·백그라운드 등 사용자가 실시간으로 지켜보지 않는 세션에서는**:
  - `data.js`/`app.js`/`sections.json`/`sitemap.xml` 등 사이트 연동 파일을 건드리지 않는다
    (4-5는 항상 사용자 승인이 필요한 단계이므로 무인 세션 범위 밖).
  - **`git push`를 하지 않는다.** 이 프로젝트는 push 시 Cloudflare Pages가 자동배포되므로,
    검증(사용자 확인)을 안 거친 배치 결과가 그대로 라이브에 올라가는 걸 막기 위함 — 로컬
    커밋까지만 하고, push는 사용자가 있는 세션에서 결과를 확인한 뒤 별도로 진행한다.
